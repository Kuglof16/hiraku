# hiraku.cfd — GPU の流体計算

設計の形を入れると、GPU の流体計算で空気抵抗と横風の 6 分力を出し、冠水路を通るときの水を解くパッケージ。外から使うのは `hiraku/tools/cfd_tools.py` (ツール `cfd_aero` と `cfd_water`) だけで、`hiraku/tools/mcp.py` の 1 行がそれを読み込む。このフォルダ・アダプタ・その 1 行を消しても、ほかは動く (`tests/cfd/test_coupling.py` が確かめる)。

本番の実行では、空力の CAE 役とまとめ役がこのツールを呼べる (`RUN_TOOLS`)。`analyze` を通らないので、値は判定の根拠にしない。

ここで出す値は、実験と比べて確かめたものではない。記録の `physically_validated` は false で、`assumptions` に「確かめていない」と書く。既定の Cd 0.8・Cy 1.0 は置き換えない。

## 解き方

- D3Q19 の格子ボルツマン法。2 枚の配列の pull 方式、32 ビット浮動小数点、分布は `h = f - w` で持つ (Lehmann et al., PRE 106, 015308, 2022)
- 衝突は正則化 (Latt & Chopard, 2006) と Smagorinsky のモデル。壁関数は地面だけで、車体の壁には無い
- 力は全ステップの運動量交換の和の差で出す。瞬間の値は奇数と偶数のステップで振れるので、結果には使わない。ゼロの状態の重みは力に入れない (地面に立つ車輪の接地面で、基準の圧力の分の偽の荷重になるため)
- 形は凸の立体の集まり (箱・管・円柱・球)。格子の線と立体の交わりで線を切るので、節点の中心が入らない 3 mm の板や細い管も、両側から流れを止める。壁の位置は線の上の距離で補間する (Bouzidi et al., 2001)。外の空気が届かない節点は固体にする。網は多孔の面として扱う
- 周りは一様流の遠方の箱で、内側に吸収層を置く。周期の境界は使わない。地面は滑る面に壁関数の応力を足し、動く地面は応力の差で効く。車輪は回転する壁の速度を持つ (節点ごとに質量を足さない形)。タイヤと地面のすき間が 1.5 格子より狭い所は箱で埋める
- 横風は空気の向きを格子の +x に固定して車を回す。車の前後軸に沿って地面が動く

## GPU

Python 標準の ctypes で、ドライバの CUDA (`nvcuda.dll`、`libcuda.so.1`) を呼ぶ。依存は増えない。GPU の無い環境ではツールが「GPU が無いので回さない」と答え、試験は理由つきで skip する。CPU では回さない。保存した記録の再生は GPU 無しで動く。

走らせる前に `nvidia-smi` の空きを測り、配列と余裕 600 MiB が入らなければ断る (`solver.check_memory`)。1 度に 1 本で、`cuda.gpu_turn()` が先着順の列を作る。

### kernels.ptx の作り直し

`kernels.ptx` は `kernels.cu` から作った生成物で、先頭の行に元のファイルの sha256 (改行の違いを除く) を書いてある。NVIDIA のドライバがあれば PTX をそのまま読めるので、実行に NVRTC は要らない。`kernels.cu` を変えたら作り直す:

```
python -m hiraku.cfd.cuda
python -m hiraku.cfd.cuda water
```

コンパイラは nvcc ではなく NVRTC (`nvrtc64_120_0.dll`、NVIDIA の `nvidia-cuda-nvrtc` 12.9 に入っている物)。探す順は、環境変数 `HIRAKU_NVRTC_DLL`、`PATH`、Python の site-packages。オプションは `--gpu-architecture=compute_75 -std=c++17`。古い印の PTX を読もうとしたときも、同じ手順で作り直す (NVRTC が無ければ、理由つきで止まる)。

## 確かめ

答えの分かっている体で回した結果は `data/validation.json` にある (値の出どころ、格子ごとの Cd、コードのハッシュ)。作り直すのは `benchmarks.py` で、`tests/cfd/test_validation.py` が GPU なしで照らす。参照値には二次の出どころのものがあり、記録にそのとおり書いてある。

| 体 | 参照値 | 格子を細かくしたときの Cd | 読み |
|---|---|---|---|
| 球 Re 100 | 1.0917 (Schiller-Naumann の経験式) | 1.199、1.148、1.122 (直径 10、14、20 格子) | 二次で収束、外挿 1.099 |
| 球 Re 1000 | 0.4383 (同じ式) | 0.678、0.572、0.515 | 二次で収束するが、この格子では高い。外挿 0.457 |
| 立方体 Re 1e5 | 1.05 (Hoerner の表の描き直し、原典は読んでいない) | 0.980、0.998、1.046 (12、16、24 格子) | 24 格子で -0.3 %、まだ格子で動く |
| 正方形の板 Re 1e5 | 1.17 (同じ) | 1.272、1.257、1.233 | 24 格子で +5.4 %、まだ格子で動く |
| Ahmed body 25 度 | 0.2875 (Ahmed の図を別の資料が読んだ値) | 0.754、0.716、0.659 (長さ 42、60、84 格子) | 不合格。2.3 から 2.6 倍。丸い鼻の肩で流れがはがれる |

角のある体は 1 割以内に入るが、丸い面ではがれる位置を計算が決める体は、この格子では確かめられていない。車体の Cd を実験と比べたものは無い。

v5 のヨー 0 での感度 (40 km/h): 格子 80、56、40 mm で抵抗 164、167、168 N (40 mm は狭い領域)。格子と車の位置のずれで 56 mm で 159 から 171 N。領域の断面を約 2 倍にすると 80 mm の平均で 164 から 154 N。`uncertainty.py` が、この幅で OK / NG が動くかの表を作る。

## 冠水路の水 (見せるための計算)

`water.py` は、一定の速さで浅い水たまりを通る車の水を MLS-MPM (Hu et al., ACM TOG 37(4), 2018, DOI 10.1145/3197517.3201293) で GPU で解く。水は弱い圧縮性の Tait の式で、音速の決まりと gamma = 7 は Wei et al. (arXiv:1702.07760) で読んだ (元の Monaghan 1994 は読んでいない)。水の密度と重力の値は `water.py` に「確かめていない」と書いてある。ほかの出どころは `water.py` の `SOURCES`。

見せるための計算で、走破の判定ではない。波の大きさは実験と比べておらず、音速を変えると車が受ける力積は動き続けるので、力の値としては読まない。確かめたのは、静止した水の水位と残留速度、移動する箱の運動量の釣り合い、計算の形と描く形が同じこと (`tests/cfd/test_water.py`)。

実行の中ではツール `cfd_water` で呼ぶ。記録 (`water_record.py`) は実行のフォルダの `cfd/v<版>/water_.../` に残り、OK / NG も基準も持たず、判定の根拠にしない。1 回に数分で、GPU が無ければ回さない。保存した記録は GPU なしで読める。

`water_coupled.py` は、同じ水と K2 の車両を双方向につなぐ (ツールの既定)。水の力を約 4 ms ごとに部品ごとに K2 へ渡し、K2 が動かした車で水が次を進む。片方向では成り立たない (水の力が車の重さに近く、車が浮いても力が減らないので裏返る)。

- 車輪の上向きの力は K2 の接地を通して車輪に渡す。回す計算では音速を上げるほど増え続けて定まらないので、回さない計算との比を掛ける (`lift_ratio_from`)。v5、30 mm、音速 200 m/s で 0.26 (確かめていない)
- 水の側の車は K2 の車体の x、z、ピッチで動き、車輪だけ K2 の位置に置く。ロールとヨーは K2 の側だけにある。左右が同じ設定なのでほぼ 0 になる
- v5、水深 195 mm、目標 18 km/h で、18.5 → 最低 11.2 km/h、路面に対して最大 3.8° 鼻が上がり、前輪は 0.6〜1.2 秒ごろ路面を離れる。実験と比べておらず、確かめていない
- 確かめたのは、車輪の力の手計算 (静止で 250 / k_z)、水の運動量の収支、車輪が路面に接して描かれること (`tests/cfd/test_water_coupled.py`)
