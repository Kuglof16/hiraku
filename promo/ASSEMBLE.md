# assemble.py — カットを 1 本の動画につなぐ

原稿 (narration.tsv) の枠を時間の軸にして、カットごとの映像 (できた動画・静止画・文字の札) を並べ、カットの境目を「つなぎ」で、暗い画面を「見た目の層」で仕上げる。最後に字幕と音を `subs.py` の焼き込みと同じ形で入れる。

```
py promo/assemble.py plan  promo/assembly.json --work <作業フォルダ>
py promo/assemble.py build promo/assembly.json <出力.mp4> --work <作業フォルダ> \
    [--height 1080|2160] [--subs <subs.ass>] [--audio <mix.wav>] [--encoder auto|nvenc|x264]
```

- `--encoder` は圧縮のしかた (下の「GPU で圧縮する」)。既定の `auto` は、NVIDIA の GPU の h264_nvenc が使えればそれ、使えなければ libx264 (CPU)。どちらになったかを最初に `encoder: nvenc` のように出す

- `plan` は時刻の表 (各カットの始まり、つなぎの始まり | 境目 | 終わり、全体の長さ) を出すだけ
- `--work` は表の中の `${WORK}` に入るフォルダ。ほかの名前は `--set NAME=VALUE`
- `--height 2160` で 4K。同じ表のまま作れる (下の「映像」の高さごとの指定を参照)
- ffmpeg は PATH か環境変数 `FFMPEG`。Python は標準ライブラリだけ
- 途中のファイルは `<出力名>.parts/` に残る (カットごとの mp4 と、字幕の前の `film.mp4`)

## 時刻の扱い

- 原稿の枠が正。カットの映像は枠の長さに合わせる: 動画が長ければ後ろを切り、短ければ最後のコマで止める
- つなぎ (長さ d) は **境目をまたいで前後に d/2 ずつ**。枠の切れ目 = つなぎの真ん中なので、全体の長さと声・字幕の時刻は変わらない
- そのため各カットは枠の前に d/2 (動画は最初のコマで止めた絵)、後ろに d/2 (動画は続きのコマ、無ければ最後のコマ) を足して作り、`xfade` の offset = 境目 − d/2 で重ねる
- d は 30 fps で偶数コマに丸める (前後に整数コマずつ割るため)。0.25 秒 → 8 コマ (0.267 秒)、0.5 秒 → 16 コマ (0.533 秒)
- 枠の時刻はコマの格子 (1/30 秒) に乗っていること。乗っていなければ止まる

## つなぎ (カットの境目ごと)

| 種類 | 見え方 | ffmpeg での作り方 |
|---|---|---|
| `cut` | 硬く切る | `concat` |
| `dissolve` | 重ねて溶ける | `xfade=transition=fade` |
| `light` | 暖かい光 (#f6ead0) が強まり、次のカットが光の中から出る | 両側のカットで: 自分の絵を `gblur` した光を `blend` (screen) で強め、続いて #f6ead0 の `color` へ `blend` で寄せる。強さは境目で 1 になる時刻の式 (smoothstep)。その上で `xfade=fade` |
| `grain` | 粒が増えて砂のように崩れ、次のカットに組み上がる | 両側のカットで: 粗い粒 (`noise` を `gblur` した灰色の層) を `blend` (overlay) で境目に向けて強める。境目は `xfade=transition=custom`: 画素ごとの切り替わりの時刻を「なめらかな値ノイズ 2 段 (斑) + 2 px の砂粒ごとの固定の乱数」で決め、斑ごとに砂のふちでほどける |

`xfade` の custom 式は `st()`/`ld()` を使わずに展開して書いている (xfade は式を複数のスレッドで同時に評価し、変数が混ざるため)。

## 見た目の層 (カットごと)

| 層 | 作り方 |
|---|---|
| `grain` (フィルムの粒) | 灰色の `color` に `noise` (明るさだけ、毎コマ変わる) をかけ、`gblur` で 1 px より少し大きい粒にし、`blend` (overlay、不透明度 0.30) で明るさに重ねる。乱数の種はそのカットの始まりのコマ番号 + 1 で、同じ入力なら同じ画素になる |
| `bloom` (光のにじみ) | `lutrgb` で明るい所 (150/255 より上) だけを残し、`gblur` (σ 18 px) でぼかして `blend` (screen) で重ねる。強さ = 表の `bloom` (不透明度) |

ぼかしの大きさや粒の大きさは 1080p の画素で決め、出力の高さに合わせて拡大する。

## 重ね (`overlay`、映像ごと)

地が透明のコマ (画面を `export.py frames ... --layer fg` で書き出した PNG の連番、または透明度を持つ動画) を、その映像の受け持つカットの頭から重ねる。N01〜N04 の番号つきのラベル (`screens/labels_n01.html` など) に使う。

```json
{"cuts": ["N01", "N02"], "video": "${WORK}/clips/n01_n02_video_1080p.mp4",
 "overlay": [{"frames": "${WORK}/frames/labels_n01", "cut": "N01"},
             {"frames": "${WORK}/frames/labels_n02", "cut": "N02"}]}
```

| 項目 | 意味 |
|---|---|
| `frames` | 拡張子の無いパスはフォルダで、中の `00000.png` から順に読む (`%05d.png`、表の `fps` で)。拡張子があれば動画 |
| `cut` | どのカットの頭から重ねるか (その映像の受け持つカットのどれか)。無ければ最初のカット |
| `at` | そのカットの頭からさらに何秒あとか (既定 0) |

- 重ねは映像の上、見た目の層 (粒・にじみ) とつなぎの前に入る。コマは出力の大きさに Lanczos で合わせる
- 始まりのコマ = 枠の前に足した分 (つなぎの半分) + (そのカットの始まり − 映像の始まり) × fps + `at` × fps。最初のコマより前と最後のコマのあとは、下の映像がそのまま出る (`overlay` の `eof_action=pass`)
- ffmpeg の入力は、映像 (札のときは無し) のあとに重ねの順で並ぶ

```
py promo/export.py frames promo/screens/labels_n01.html <作業>/frames/labels_n01 --fps 30 --layer fg --scale 1
```

## 字幕と音

`--subs` があれば `promo/subs.py` の `burn_command` で、つないだ映像の上に帯と字幕を焼き、`--audio` の音を入れる (字幕はつなぎの上に乗る)。`--subs` が無ければ映像はそのままで、`--audio` があれば音だけ入れる。

## 組み立ての表 (JSON)

見本は `promo/assembly.json` (いまの 21 カット)。

```json
{
  "script": "${WORK}/script/narration.tsv",
  "fps": 30,
  "band": {"top": 910, "color": "#1b1a17"},
  "default_join": {"kind": "dissolve", "seconds": 0.25},
  "segments": [
    {"cuts": ["N00"], "video": {"1080": "${WORK}/clips/n00_1080p.mp4", "2160": "${WORK}/clips/n00_2160p.mp4"},
     "join": {"kind": "dissolve", "seconds": 0.3}},
    {"cuts": ["N01", "N02"], "video": "${WORK}/clips/n01_n02_video_1080p.mp4"},
    {"cuts": ["N03"], "still": "${WORK}/storyboard/layouts/_tools/png/N03.png", "paint_band": true},
    {"cuts": ["N17b"], "paint_band": true,
     "card": {"background": "#131311", "lines": [
       {"text": "…", "x": 160, "y": 300, "size": 64, "font": "C:/Windows/Fonts/YuGothB.ttc", "color": "#f1ece0"}]},
     "look": {"grain": true, "bloom": 0.35},
     "join": {"kind": "light", "seconds": 0.6}}
  ]
}
```

| 項目 | 意味 |
|---|---|
| `script` | 原稿。相対パスなら表のファイルからの相対 |
| `fps` | 既定 30 |
| `band` | `paint_band` で塗る下の帯 (1080p での y と色)。絵コンテの下絵に描かれた字幕を消すため |
| `default_join` | `join` を書かないカットの、次へのつなぎ |
| `segments[].cuts` | この映像が受け持つカット (原稿の順に、抜けなく)。複数なら枠を続けて 1 本 |
| `video` / `still` / `card` | どれか 1 つ。`video` は文字列か、高さごとの `{"1080": …, "2160": …}` (無い高さは一番大きいものを拡大) |
| `card` | 文字の札: 背景色と行 (`text`・1080p での `x` `y` `size`・`font` のファイル・`color`) |
| `paint_band` | 下の帯を塗る |
| `look` | `{"grain": true/false, "bloom": 強さ 0〜1}` |
| `join` | 次のカットへのつなぎ: `{"kind": "cut|dissolve|light|grain", "seconds": 秒}`。最後のカットのものは使わない |
| `overlay` | 地が透明のコマの重ね: `{"frames": …, "cut": …, "at": 秒}` か、その並び (上の「重ね」) |

表の検査 (作る前に止まる): カットが原稿と同じ順で抜けなく並ぶこと、枠が続いていること、つなぎの半分が前後の枠の半分より短いこと、置き換えの名前に値があること、重ねに `frames` があり `cut` がその映像のカットであること。

## GPU で圧縮する・フィルタを軽くする

### 選ぶ規則 (`--encoder`)

| 値 | 動き |
|---|---|
| `auto` (既定) | ffmpeg の `-encoders` に h264_nvenc があり、256×144 の 0.2 秒の試しの圧縮が通れば `nvenc`。どちらかがだめなら `x264` |
| `nvenc` | h264_nvenc。使えなければ止まる (x264 に黙って戻さない) |
| `x264` | libx264。前と同じ引数 |

カットごとのファイル・つないだ `film.mp4`・字幕を焼いた最後のファイルの 3 つとも、選んだもので圧縮する (字幕の焼き込みは `subs.py` の `burn_command` の libx264 の部分だけを入れ替える)。`export.py encode`・`clip` にも同じ `--encoder` がある。

### NVENC の設定 (`export.py` の `nvenc_args`)

`-c:v h264_nvenc -preset p7 -tune hq -rc vbr -cq <CRF と同じ値> -b:v 0 -maxrate 240M -bufsize 480M -spatial-aq 1 -temporal-aq 1 -rc-lookahead 32 -bf 3 -b_ref_mode middle -profile:v high -pix_fmt yuv420p`

- `-cq` は x264 の CRF と同じ数 (カットとつなぎは 10、字幕の焼き込みは 16、`export.py` は `--crf` の 14)。下の表のとおり、測った 5 つの組で、同じ数の `-cq` は可逆の元に対する SSIM と PSNR が x264 と同じか高かった
- `-maxrate` を書かないと、`-b:v 0` の VBR は粒のカットで約 17 Mb/s (11.9 MB / 166 コマ = 5.53 秒) に抑えられ、`-cq` 8〜14 のどれでも同じ 11.9 MB のファイルになり、SSIM が x264 より低かった (0.9497、x264 は 0.9603)。240 Mb/s は、cq 10 の粒のカット (59.3 MB / 5.53 秒 = 約 86 Mb/s) より十分上の天井として選んだ値。H.264 の level の上限との関係は確かめていない
- `-pix_fmt yuv420p` は `nvenc_args` の外で、呼ぶ側 (カット・つなぎ・`export.py`、字幕の焼き込みは `burn_command` のもの) が付ける
- 測った値 (2026-11-03、RTX 5070、ffmpeg N-125875。元は可逆 (FFV1) の 1080p。SSIM・PSNR は ffmpeg の ssim・psnr フィルタで元と比べた全体の値):

| 元 | 圧縮 | SSIM | PSNR (dB) | 大きさ (MB) | CPU (秒) |
|---|---|---|---|---|---|
| N05 のカット (粒あり、166 コマ) | x264 crf 10 medium | 0.96030 | 32.25 | 72.6 | 54.6 |
| 同じ | nvenc cq 10 | 0.96044 | 32.26 | 59.3 | 7.3 |
| N06 のカット (静止画、363 コマ) | x264 crf 10 medium | 0.99964 | 49.41 | 1.02 | 10.0 |
| 同じ | nvenc cq 10 | 0.99980 | 49.72 | 1.59 | 4.3 |
| N05 のカット (字幕の焼き込みの設定) | x264 crf 16 slow | 0.95091 | 32.14 | 27.9 | 79.9 |
| 同じ | nvenc cq 16 | 0.95544 | 32.21 | 29.2 | 6.7 |
| N18 のコマ (`export.py`、270 コマ) | x264 crf 14 slow animation | 0.99875 | 50.81 | 0.48 | 17.1 |
| 同じ | nvenc cq 14 | 0.99946 | 51.31 | 3.08 | 5.2 |
| アプリの再生のコマ (`export.py`、270 コマ) | x264 crf 14 slow animation | 0.99902 | 48.32 | 1.12 | 14.3 |
| 同じ | nvenc cq 14 | 0.99946 | 48.66 | 2.04 | 6.6 |

静かな画面では NVENC のファイルが x264 の 1.6〜6.4 倍になる (同じ画質を保つため)。4K (2160) では測っていない。

### フィルタで変えたこと

測ると、遅いのは圧縮ではなく、時刻 T を含む式の `blend` (光のつなぎと粒のつなぎ) だった。式は画素ごとに評価され、前はつなぎの無いコマでも全部のコマで走っていた (強さ 0 で絵は変わらない)。N05 (166 コマ、粒・にじみ・粒のつなぎ・光のつなぎあり、`-f null` でフィルタだけ):

| 前のやり方で、残した層 | 経過 (秒) |
|---|---|
| 土台 (読み込み・拡大・帯) だけ | 9.7 |
| 土台 + にじみ (bloom) だけ | 17.6 |
| 土台 + 粒 (grain) だけ | 20.7 |
| 土台 + 粒のつなぎだけ | 26.3 |
| 土台 + 光のつなぎだけ | 140.6 |
| 全部 | 393.2 |

(この表はほかの ffmpeg が動いている間に測ったので、値は大きめ。比は同じ回の中で比べられる)

直したこと (`segment_graph(..., fast=True)`、既定):

1. 光のつなぎ・粒のつなぎの `gblur` と `blend` に `enable` を付け、強さが 0 より大きくなりうるコマ (と前後半コマ) だけで走らせる (`ramp_window`)。ほかのコマでは前の式も A をそのまま返すので、そのコマの画素は前と同じ。粒のつなぎの `noise` は全部のコマで走らせたまま (乱数の並びを前と同じにするため)
2. 粒 (grain) の `blend` を式から組み込みの `c0_mode=overlay:c0_opacity=0.300` に。同じ式だが丸めが違い (組み込みは整数の割り算)、可逆で比べた N05 の SSIM が 1 にならないのはこのため (下の表、最小 0.99768)

`fast=False` で前のフィルタになる (比べるため)。どちらも同じ乱数の種を使う。

新しいフィルタの N05 (同じ 166 コマ、ほかの ffmpeg がほぼ動いていない時。それぞれ土台 + その層だけ): 土台 0.39 秒、にじみ 1.26 秒、粒 0.84 秒、光のつなぎ 4.23 秒、粒のつなぎ 1.36 秒、全部 6.67 秒 (CPU 59.6 秒)、x264 で圧縮まで 8.77 秒 (CPU 113.8 秒)。残りの重さはにじみの `gblur` (1 秒足らず) と光のつなぎの数コマの式で、次の手は使っていない:

- (a) 縮めた絵でぼかす / (b) `gblur_vulkan`: にじみのぼかしは 166 コマで 0.9 秒ほどで、ffmpeg の `gblur` はσによらず手間が同じ (再帰型) ため、縮めても GPU に移しても得が小さい。`gblur_vulkan` は別のぼかし方で絵が変わり、絵を GPU へ送り返す手間もかかる
- (c) `-hwaccel cuda` の読み込み: 読み込みと拡大を合わせて 166 コマで 0.39 秒 (CPU 3.4 秒) なので入れていない
- 光のつなぎの式・`lutrgb`・`noise` には GPU 版が無い

### 前と後 (全体の組み立て)

`assembly.json`、本人の声 (`--subs subs/recorded/subs.ass --audio animatic/mix_recorded.wav`)、1080p、2026-11-03。測る前に tasklist で、ほかの ffmpeg が CPU を使っていない (出ては消える短いものだけ、CPU 時間 0:00:00) ことを確かめた。CPU 時間は各 ffmpeg の利用者 + カーネルの時間 (GetProcessTimes) の合計。

| | 前 (x264、前のフィルタ) | 後 (nvenc、新しいフィルタ) |
|---|---|---|
| 全体の経過 | 2317.9 秒 (38.6 分) | 292.1 秒 (4.9 分) |
| ffmpeg の CPU 時間 | 6122.3 秒 | 679.7 秒 |
| うちカットのファイル 20 本 (21 カット) | 1924.0 秒 / CPU 5115.0 秒 | 246.2 秒 / CPU 518.1 秒 |
| つなぐ (`film.mp4`) | 179.3 秒 / CPU 486.4 秒 | 21.7 秒 / CPU 102.7 秒 |
| 字幕と音 | 214.6 秒 / CPU 521.0 秒 | 24.2 秒 / CPU 58.8 秒 |

後のほうでは、N00 (19.3 秒、CPU 5.0 秒) や N10 (15.7 秒、CPU 2.9 秒) のように経過が CPU 時間よりずっと長いカットがあった。なぜ待っているかは調べていない。

### 見た目が変わらないこと

可逆 (FFV1) で書いて、フィルタだけを比べた (前のフィルタ 対 新しいフィルタ、コマごとの SSIM):

| カット | 最小 | 平均 |
|---|---|---|
| N05 (粒・にじみ・粒のつなぎ・光のつなぎ) | 0.99768 | 0.99833 |
| N06 (光のつなぎの入り) | 1.00000 | 1.00000 |
| N10 (見た目の層なし) | 1.00000 | 1.00000 |

全体の前と後 (圧縮も違う) の、同じコマの SSIM (All):

| 時刻 | 見た目の層 | SSIM |
|---|---|---|
| N03 (22.0 s)・N06 (40.0 s)・N10 (86.0 s)・N13 (120.0 s) | なし | 0.99932・0.99853・0.99935・0.99906 |
| N05 (31.0 s)・N08 (63.5 s)・N08b (72.0 s)・N17b (159.5 s)・N18 (167.0 s) | あり | 0.97734・0.97910・0.98074・0.98138・0.97786 |
| 粒のつなぎ N04→N05 (28.467・28.6・28.733 s) | あり | 0.99296・0.98970・0.98162 |
| 光のつなぎ N05→N06 (33.467・33.6・33.733 s) | あり | 0.97052・0.98788・0.99512 |
| 光のつなぎ N08b→N09 (77.0 s)・粒のつなぎ N17→N17b (156.6 s) | あり | 0.99108・0.98985 |
| 光のつなぎ N17b→N18 (162.2・162.4 s) | あり | 0.97885・0.98412 |

見た目の層のないカットは 0.99 以上。層のあるカットは 0.97734〜0.98138、つなぎのコマは 0.97052〜0.99512 で、目安の 0.98 を下回るコマがある (いちばん低いのは 33.467 s の 0.97052)。原因はフィルタではなく粒の圧縮: 粒は毎コマ違う乱数の細かい模様で、圧縮はそれを元どおりには残せず、x264 と NVENC は別の残し方をする。N05 のカットのファイルを、前のフィルタの可逆の絵と比べると、前 (x264) が平均 0.95771・最小 0.76776、後 (nvenc) が平均 0.95716・最小 0.77256 で、どちらも同じだけ元から離れている。前と後どうしの差 (平均 0.98421) は、この 2 つの離れ方の違い。前と後を同じに近づけたいなら、途中のファイル (カットと `film.mp4`) を可逆で書き、最後の 1 回だけ圧縮する (この変更ではしていない)。並べた見比べ (N05・光のつなぎの真ん中・粒のつなぎの真ん中・N18、前と後) では違いが見えなかった。

## 試験

```
python -m unittest promo.tests.test_assemble
```

表の読み込み、時刻 (境目がつなぎの真ん中・全体の長さが変わらない)、フィルタの組み立て、重ねの始まりのコマを ffmpeg 無しで確かめる。ffmpeg と ffprobe があるときは、小さな入力から 3 秒の動画を 2 回作り、コマ数と、2 回のコマの画素が同じこと (粒の乱数が固定) を確かめる。重ねは、暗い静止画の 2 つ目のカットの 0.2 秒あとから 12 コマの白い四角を重ね、四角がそのコマ (36〜47) にだけ出ることを確かめる。

GPU まわり: x264 の引数が前と同じこと、nvenc の引数 (`-cq` = CRF、yuv420p)、字幕の焼き込みの圧縮だけが入れ替わること、つなぎの式を走らせるコマが強さ 0 より大きいコマをすべて含むこと (Python で式を評価して確かめる)、新しいフィルタと前のフィルタを可逆で書いてコマごとの SSIM が 0.99 以上。h264_nvenc が使える所では、同じ 3 秒の動画を nvenc で作り、H.264・yuv420p・90 コマ・3.0 秒であること、粒の無いコマで x264 との SSIM が 0.99 以上であることを確かめる (使えない所では飛ばす)。
