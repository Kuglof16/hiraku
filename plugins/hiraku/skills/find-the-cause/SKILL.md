# 食い違いの原因を書く

食い違いは失敗ではなく、どちらかの数字をまだ信用できないという知らせ。原因を書くまで、その分野の `analyze` と `compare` は止まる。

## 1. 差の大きさと向きを見る

`compare` の結果の `predicted`・`analyzed`・`diff_rel`・`tolerance_rel` を読む。

- 10 倍・100 倍・1000 倍近く違う → 単位か桁の取り違えを先に疑う (例: 重心の高さ 62 cm を 62 mm と入れた)
- 2 倍・1/2 倍近い → 荷重を何本の輪・何本のレールで分けたか、片側か両側か
- 数十 % → 手計算のモデルが単純すぎる (単純支持の梁と、横材で荷重を分け合うフレーム、など)
- 符号が逆 → 力の向き・座標の向き (x 前・y 左・z 上) の取り違え

## 2. 予測の側を見直す

- その予測を記録したとき `record_prediction` が返した記録 (`inputs`・`assumptions`) を読み直す
- 入力の値と単位が、写したもとの値 (要件・設計・前の記録) と同じか
- 式の前提 (`list_formulas` の `assumptions`) が、この荷重条件に合っているか

## 3. 解析の側を見る

- `records.analyses` の結果の `where` (どの部材・どの輪で最大か) が、手計算で考えた場所と同じか
- ツールがどこに荷重をかけ、どこで支えたか (荷重条件の `params`、上流の解析の結果)

## 4. 書く

`record_cause(comparison_id, cause, fix)`:

- `cause`: 何が違っていたかを 1 文で。分かっていない所は「確かめていない」と書く。推測を事実のように書かない
- `fix`: 次に何を変えるか (予測の前提か入力を直す、別の式を使う、設計を直す)
- シェルのホットスポットが梁の式を大きく超えたつなぎ目なら、別の式は `frame_static.joint_wall_bending` で、入力は `get_context(sections=["joint_wall_inputs"], load_case_id=...)` から写す (skill `hiraku:predict-then-analyze` の 2b)

## 5. やり直すか、安全側として合否を出すか

ふつうはやり直す:

- 直した前提と入力で `record_prediction` を記録し直し、その ID で `analyze` → `compare`
- 一致すれば、前の原因はツールが自動で「解決」にする

食い違ったままでも合否を出してよいのは、次の 2 つが両方そろうときだけ:

1. 原因で差が説明できる: どの前提がどちら向きに数字をずらしたかが言える (例: 鉛直の曲げは合っていて、外れているのは継ぎ手を固定とみた分の横の曲げとねじりだけ)
2. その前提では、予測が本当の値を安全側から押さえていると判断できる: 前提がずらすのは不利な側にだけ (例: 継ぎ手を固定とみるとレールは実際より硬く、受け持つ曲げとねじりが大きく出る)

そのときは `record_cause` に `safe_side: true` と `safe_side_reason` (上の 2 つを、どの前提がどちら向きにずらすかで書く) を付ける。ツールが数字の向きを確かめ (基準が ≤ なら予測 ≥ 解析、≥ なら予測 ≤ 解析)、合っていれば予測 (不利な方の値) で合否を作る。向きが逆ならツールは断る。そのときは安全側ではないので、safe_side を外して原因を書き、直した式で予測し直す。

原因は説明できても、この実行で確かめられる予測がその量に届かない (手計算で解けない、など) ときは、`record_cause` に `ends_case: true` を付ける。その荷重条件は判定なしで終わり、終わりも重い段も待たない。タイルは判定なしのまま、緑にはならない。`safe_side` とは一緒に付けない。

やってはいけないこと:

- 差が説明できないまま safe_side を付ける。「大きめに出ているから安全」は理由にならない
- 一致させるために式を作り込む (係数を足す、入力を合う値に寄せる)。式を変えるのは、抜けていた物理を入れるときだけ
- 合否の基準や許す幅を変えようとする (荷重条件で決まっていて、変えられない)
