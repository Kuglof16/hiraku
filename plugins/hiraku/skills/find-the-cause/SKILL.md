# 食い違いの原因を書く

食い違いは失敗ではなく、どちらかの数字をまだ信用できないという知らせ。原因を書くまで、その分野の `analyze` と `compare` は止まる。

## 1. 差の大きさと向きを見る

`compare` の結果の `predicted`・`analyzed`・`diff_rel`・`tolerance_rel` を読む。

- 10 倍・100 倍・1000 倍近く違う → 単位か桁の取り違えを先に疑う (例: 重心の高さ 62 cm を 62 mm と入れた)
- 2 倍・1/2 倍近い → 荷重を何本の輪・何本のレールで分けたか、片側か両側か
- 数十 % → 手計算のモデルが単純すぎる (単純支持の梁と、横材で荷重を分け合うフレーム、など)
- 符号が逆 → 力の向き・座標の向き (x 前・y 左・z 上) の取り違え

## 2. 予測の側を見直す

- その予測を記録したとき `record_prediction` が返した記録 (`inputs`・`assumptions`) を読み直す
- 入力の値と単位が、写したもとの値 (要件・設計・前の記録) と同じか
- 式の前提 (`list_formulas` の `assumptions`) が、この荷重条件に合っているか

## 3. 解析の側を見る

- `records.analyses` の結果の `where` (どの部材・どの輪で最大か) が、手計算で考えた場所と同じか
- ツールがどこに荷重をかけ、どこで支えたか (荷重条件の `params`、上流の解析の結果)

## 4. 書く

`record_cause(comparison_id, cause, fix)`:

- `cause`: 何が違っていたかを 1 文で。分かっていない所は「確かめていない」と書く。推測を事実のように書かない
- `fix`: 次に何を変えるか (予測の前提か入力を直す、別の式を使う、設計を直す)
- シェルのホットスポットが梁の式を大きく超えたつなぎ目なら、別の式は `frame_static.joint_wall_bending` で、入力は `get_context(sections=["joint_wall_inputs"], load_case_id=...)` から写す (skill `hiraku:predict-then-analyze` の 2b)

## 5. やり直すか、安全側として合否を出すか

ふつうはやり直す:

- 直した前提と入力で `record_prediction` を記録し直し、その ID で `analyze` → `compare`
- 予測との判定が OK になれば、前の原因はツールが自動で「解決」にする

食い違ったままでも合否を出してよいのは、次の 2 つが両方そろうときだけ:

1. 原因で差が説明できる: どの前提がどちら向きに数字をずらしたかが言える (例: 鉛直の曲げは合っていて、外れているのは継ぎ手を固定とみた分の横の曲げとねじりだけ)
2. その前提では、予測が本当の値を安全側から押さえていると判断できる: 前提がずらすのは不利な側にだけ (例: 継ぎ手を固定とみるとレールは実際より硬く、受け持つ曲げとねじりが大きく出る)

そのときは `record_cause` に `safe_side: true` と `safe_side_reason` (上の 2 つを、どの前提がどちら向きにずらすかで書く) を付ける。ツールが数字の向きを確かめ (基準が ≤ なら予測 ≥ 解析、≥ なら予測 ≤ 解析)、合っていれば予測 (不利な方の値) で合否を作る。向きが逆ならツールは断る。そのときは安全側ではないので、safe_side を外して原因を書き、直した式で予測し直す。

手計算が値に届かないとき (式が無い、上から押さえるだけでゆるくて限界を超えてしまう、原因が「手計算では届かない」) は、手計算の役目を「力の道がつながっているか」を確かめることに切り替える。手計算は、何も考えずに CAE を回さないためのもの:

1. 力の道を手計算で確かめる: その版で `record_prediction` に `load_path.free_parts` (部品から部材まで、触れている所をたどって、つながらない部品を数える) を記録する。0 なら道はつながっている
2. 道をたどるツールの解析 (load_path など、`free_parts` か `unsupported_load` を出すもの) が、その荷重条件で、支えのない荷重 (`unsupported_load`) を出していないこと
3. `record_cause` に `tool_decides: true` と `tool_decides_reason` (なぜ手計算が値に届かないか) を付ける。ツールが道の確かめを見て、通っていればツールの値で合否を作る (`path_checked`。OK も NG もある)。道の確かめが無いか通っていなければ断る

上から押さえる式 (例: `load_path.grip_bound`) が限界を超えても、それは式がゆるいだけのことがある。ツールの値が限界より十分小さく、差が「上から押さえた分のゆるさ」で説明できるなら、上の 1〜3 で、ツールの値で合否を出す。`tool_decides` は `safe_side` とも `ends_case` とも一緒に付けない。

道の確かめもできない (道を数える手計算もツールも無い) ときだけ、`record_cause` に `ends_case: true` を付ける。その荷重条件は判定なしで終わり、終わりも重い段も待たない。タイルは判定なしのまま、OK にはならない。道が確かめてある版で `ends_case` を付けると、ツールは断って `tool_decides` を勧める。

## 手計算が予測していない場所の NG (hot_spot)

ツールはモデルの全体を見て、利用率 (値 / 許し) の高い順に場所を `hot_spots` に並べる。手計算は見たい所だけを見るが、CAE は手計算が見ようと思っていなかった所を見つけるのも役目。予測していない場所 (`predicted: false`) で基準の量が許しを超えると、ツールは解析のときに NG の合否を作る (`basis: "hot_spot"`、`where` にその場所)。

1. その場所で何が起きているかを、解析の結果 (場所ごとの値、力、`assumptions`) で確かめる。どの力が、どの部材・金具・溶接を、どう曲げるか引っぱるか。
2. `record_cause` に `verdict_id` (その NG の合否の ID) と `cause`・`fix` を書く (`comparison_id` は付けない)。`fix` は設計役が変えられるもの (板厚・脚長・部材の形など) で書く。`safe_side`・`tool_decides`・`ends_case` は付けない (予測との判定が無いので)。
3. 直した版でその場所が許しの内になれば、NG は消える。タイルが道の確かめ (`load_path.free_parts`) も求めていれば、それも記録する。
4. 尖りの点 (細かくすると上がる要素の最大、note つきの行) は、基準の量の行ではないので NG にならない。原因を書く対象でもない。

やってはいけないこと:

- 差が説明できないまま safe_side を付ける。「大きめに出ているから安全」は理由にならない
- 一致させるために式を作り込む (係数を足す、入力を合う値に寄せる)。式を変えるのは、抜けていた物理を入れるときだけ
- 合否の基準や許す幅を変えようとする (荷重条件で決まっていて、変えられない)
